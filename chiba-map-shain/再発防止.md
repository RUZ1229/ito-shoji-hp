## 機能追加の手順（原則）

1. `千葉配送地図_他社/` で実装・確認
2. **同じ変更を** `千葉配送地図/` に反映（または `build_chiba_map_distrib_pack.py` の同期）
3. `build_chiba_map_data.py` … **省略時は両系統**の `map_data.json` を更新
4. zip・オンライン公開 … 配布パック生成 → **自動** `deploy_chiba_map_live`（顧客登録・`--publish-live` 時。省略: `CHIBA_MAP_SKIP_DEPLOY=1`）
5. 社長報告 … **両方更新したか**、**意図的差分を入れたか** を1行で書く

**片方だけ・差分あり** … 社長の明示指示がある場合のみ。

## 日付の考え方（基本＝出荷日）— 社長方針（2026-09-10 確定）

**配達日ではなく出荷日を正本にする。** 日次・地図・登録のキー／表示期間はすべて **出荷日ISO**（配車依頼書の出荷予定日）。

| 対象 | キー／表示 | 備考 |
|------|------------|------|
| `配車重量_登録済.json` | **出荷日** | 1出荷日＝1エントリ。二重防止も出荷日 |
| `配車重量_日次明細.json` ／ 一覧 ／ 閲覧HTML | **出荷日** | 各ブロック内に `delivery_date` は参考表示のみ |
| 地図 **運送回数** | **出荷日** | 開始＝各現場の最早出荷日（バラバラで正しい）。**終了＝全現場共通の最新出荷日**（`last_visit`・配送回数更新のたび map 再生成で揃える） |
| 地図 **配送重量** | **出荷日** | `weight_period_start`〜`end` は登録済の出荷日範囲。ポップアップの kg 横の日付も出荷日 |
| 配送回数カウント | **出荷日** | 顧客登録時 `update_site_visit_counts`（同一出荷日は +1 のみ） |

**内部集計（地図表示には使わない）** … 現場マスタの `dispatch_weight_monthly` は配達月、`dispatch_weight_by_delivery` は配達日キー。社長・現場が見る日付は **出荷日**。

**2026年9月の起点** … 重量・日次・地図表示は **9/1出荷から**（8/31出荷分は対象外・削除済）。以降も「何月から見せるか」は社長判断。

**NG（再発）** … 日次キー・地図期間・運送回数を **配達日** で揃える  
**NG（再発）** … 日次閲覧・地図で配達日を選ぶ前提の説明（**出荷日で見る**）

**確認** … `配車重量_日次閲覧.html` の日付セレクト＝出荷日。地図 `map_data.json` の `weight_period_*` が登録済出荷日と一致。

## 顧客登録（配送回数・地図）— 社長方針（2026-09-10 確定）

**これからの運用** … **顧客登録したタイミングで配送回数も更新する。** 15時 `_01` でも 17時 `_02` でも同じ。

| タイミング | やること |
|------------|----------|
| **`register_course_sites.py`（顧客登録）** | ①本登録（新規・別名・住所統合） ②**配送回数**（出荷日単位・`update_site_visit_counts`） ③**地図 deploy**（本登録後・必須） |
| **17時 `_02` 到着時** | **重量・日次**（出荷日未登録時のみ）＋必要なら **地図 deploy もう1回**（本登録後と最大2回でよい） |

**配送回数の正本タイミング** … **顧客登録**。ログ `出現回数: 出荷日 … / +N現場` を確認。

**二重防止** … 同一出荷日は `dispatch_visit_dates` で再実行しても加算しない（17時自動処理が後から走っても安全）。

**17時依頼書 ≠ 必ず重量** … 書込・分割・振り分け等、指示は様々。**重量登録専用で送るわけではない**（未登録出荷日だけ重量・日次を更新）。

**正本スクリプト** … 顧客登録 `register_course_sites.py`／17時自動 `evening_dispatch_auto.py`

| 3 | `version.json` の `built` が **今日の日時** | `広報/HP/chiba-map/version.json` **と** `chiba-map-shain/version.json` |
| 4 | 公開URLの `built` と一致 | **他社** `…/chiba-map/version.json` **＋社内** `…/chiba-map-shain/version.json`（反映に数分かかることがある） |
| 5 | `map_data` の `generated` が作業直後 | 上記 **2 URL** の `data/map_data.json`（協調編集・消去は特に必須・事例20） |
| 6 | 相手側の挙動 | 古いタブで開いたまま →「新しい版があります。再読込します…」または再アクセスで反映 |

**NG（再発）** … `build_chiba_map_data.py --overrides-only` **だけ**で終了（ローカルは新しいが **GitHub Pages は古いまま**）  
**NG（再発）** … **重量登録**で `sync_map_from_master` **だけ**（事例11）  
**NG** … `chiba-map.js` を社内だけ直して **HP 4系統未同期**  
**NG** … `loadMapDataOnce` で **GitHub Pages だけ** version チェックをスキップする（事例10）  
**NG（再発）** … **他社 Pages だけ** curl して社長に「反映済」と報告（**社内 URL 必須**・事例20）

### JS 実装の鉄則（オンライン・`chiba-map.js`）

GitHub Pages（`IS_WEB_HOST`）でも **必ず** `version.json` と照合する。

| 関数 | ルール |
|------|--------|
| `maybeReloadForLatestBuild` | `!pageBuild \|\| ver.built > pageBuild` で新版HTMLを検知 |
| `loadMapDataOnce` | **IS_WEB_HOST でも** 上記と同様に `built` を照合（早期 return 禁止） |
| `startLiveVersionWatch` | `!current \|\| v.built > current` でポーリング（20秒） |

**確認** … `node --check js/chiba-map.js`（4系統）。`grep 'if (IS_WEB_HOST) { return data' js/chiba-map.js` が **0件**であること。
